# ADR-0002: 外部公式 AI ハーネスの子プロセス統合と共通アダプター層（ハイブリッドプロトコル）

- **ステータス**: Accepted（各プロバイダーの詳細プロトコル・利用条件は Phase 0 で実機検証）
- **日付**: 2026-11-25
- **関連フェーズ**: Phase 0 / Phase 2

## コンテキスト（背景・課題）

FormulaDesk は専用バックエンドサーバーや独自ユーザー登録を持たず、特定の AI プロバイダーにも依存しない設計を目指す。またユーザー自身の既存 AI サブスクリプション利用を優先しつつ、各プロバイダーの利用規約・認証仕様を厳守する必要がある。一方で、OpenAI Codex、Anthropic Claude Code、Google Antigravity、カスタム ACP エージェントは接続プロトコル・認証方式・対応機能が異なる。

## 決定内容

- 独自 AI ハーネスは開発せず、ユーザーが公式手順でインストール・認証したハーネスを外部子プロセスとして起動・管理する（T3 Code の BYO-Credentials 思想を参照）。
- Rust 側に共通の `AgentAdapter` trait、`AgentEvent` 統一イベント、`AgentCapabilities`（Capability Negotiation）を設ける。
- すべてのプロバイダーを無理に単一プロトコルへ統一せず、**ハイブリッド接続方式**を採用する：
  - OpenAI Codex: `codex app-server`（JSON-RPC 2.0 / `stdio`）
  - Google Antigravity / Custom ACP: 公式 ACP（`agent-client-protocol` Rust クレート / JSON-RPC 2.0 / `stdio`）
  - Anthropic Claude Code: 公式プロセス / Agent SDK / ACP アダプター（利用規約上の認証制約を遵守し、許可された方式のみ有効化）
- テスト用に `MockAdapter` を併設し、CI と実接続検証を明確に分離する。

## 検討した代替案

1. **各社 REST API を直接実装（API キー専用）**: サブスクリプション優先方針を満たせず、プロバイダーごとのツール呼び出し・エージェントループを自前保守する負担が大きい。
2. **全プロバイダーを非公式 ACP ラッパーへ強制統一**: 公式サポート外や認証トークン流用につながり、規約違反・保守破綻リスクが高い。

## 結果・トレードオフ・リスク

- **利点**: 公式認証フローへ委譲でき、プロバイダー追加・仕様変更の影響をアダプター層に局所化できる。
- **リスク**: 各ハーネスのバージョンアップや利用規約変更（特にサードパーティクライアントでのサブスクリプション利用可否）への継続的追従が必要。Phase 0 で最新条件を確認し、確認済み認証方式のみ有効化する。
